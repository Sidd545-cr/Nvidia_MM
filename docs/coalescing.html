Why arr2 is coalesced even though the loop walks down a column

Each thread does walk down a column of B over time. Coalescing does not look at that. It looks at the addresses that all threads of a warp request in the same instruction, at the same loop step i. Switch between the two views below and watch the memory row at the bottom of each panel.

What to take away

    
CPU: there is one thread, so what matters is how its addresses change from one loop step to the next. That is why matrix_cpu.c uses the i-k-j order.

    
GPU: a warp runs the loop in lockstep. At each step, the hardware gathers the 32 addresses from one load instruction and fetches every 32-byte sector they touch. What matters is how the address changes from one thread to the next.

    
With threadIdx.x on the column, neighbouring threads read neighbouring columns of the same row of B: one contiguous run. Over time each thread moves down a row, so the warp sweeps B one full row per step. A is the same element for every thread with the same row, so it is a broadcast.

    
The diagram uses 8 threads per row to stay readable. In the real kernel a warp is 32 threads: 16 values of threadIdx.x for each of 2 values of threadIdx.y, with 16×16 blocks. The pattern is the same.
